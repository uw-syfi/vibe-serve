# VS Meta Opt Diagnosis and Control Levers

## Attribute Before Intervening

Identify the smallest VibeSys-owned mechanism that explains the observed trajectory. Do not recommend a generic prompt change when the evidence points to evaluator semantics, missing instrumentation, session lifecycle, or candidate difficulty.

Ask:

1. Was the next decision poor given evidence available then?
2. Was the decision sound but implemented or activated incorrectly?
3. Was valid evidence produced but routed, interpreted, or retained incorrectly?
4. Did deterministic infrastructure consume agent judgment or campaign budget?
5. Is the pattern recurring and general enough for a system change?

If none fits cleanly, classify the mechanism as `Other` and explain what the taxonomy misses.

## Map Symptoms to Levers

| Observed VibeSys behavior | Candidate system lever |
| --- | --- |
| Repeated low-information tuning | Hypothesis lease, plateau trigger, designer re-entry |
| Hypothesis churn without implementation depth | Persistent implementer session, clearer proof/disproof ownership |
| Repeated inactive changes | Activation contract, bounded repair, evaluator instrumentation |
| Duplicate benchmarks across roles | Focused/official evidence authority and cadence |
| Good tradeoffs discarded | Multi-objective retention and trusted frontier policy |
| Invalid results promoted | Provenance, accuracy gates, judge evidence schema |
| Long agent turns with repeated history | Path-based context, compact artifacts, delta continuations |
| Rebuilt environments or repeated deployment setup | Framework-owned fingerprinted caches and bounded resource reuse |
| Recovery work authored repeatedly by agents | Deterministic snapshot, restore, replay, and cleanup operations |
| Judge cost without changed dispositions | Risk-triggered cadence and narrower review input |
| Repeated rediscovery after session renewal | Durable runtime docs, scripts, or selectively loaded skills |
| Search anchored to incumbent structure | Neutral interfaces and explicit permission for substrate changes |
| Recurring uncategorized pattern | `Other`, new instrumentation, then possible taxonomy extension |

Treat this table as a starting vocabulary, not a lookup that proves causality.

## Choose the Correct Change Surface

### Framework code

Use for deterministic mechanics, typed contracts, provenance, evaluation, snapshots, lifecycle, budgets, retries, and cleanup.

### Agent prompts

Use only for stable role semantics, decision procedures, evidence requirements, constraints, output schemas, and instructions for discovering skills or artifacts.

Keep prompts neutral. Do not encode:

- A candidate optimization or implementation recipe.
- A bottleneck discovered in a prior run.
- A benchmark-specific trick or known winning design.
- Hidden evaluator behavior or answers.
- Domain knowledge that can be supplied selectively.

Encoding these in an always-on prompt leaks answers into later campaigns and prevents honest evaluation of VibeSys's search ability.

### Skills available to VibeSys

Adding or improving skills is allowed. Use skills for reusable methods, domain knowledge, diagnostic workflows, and tool procedures. Keep them:

- Modular and discoverable by name or path.
- Selectively loaded rather than pasted into every prompt.
- Versioned with the VibeSys system configuration.
- General within their stated domain rather than tied to one benchmark instance.
- Auditable so gains can be attributed to capability versus orchestration.

When a skill change intentionally teaches a new reusable technique, record that as the system intervention. Do not misattribute the resulting gain to better planning policy.

### Runtime manuals and adapters

Use for environment- or provider-specific commands and capabilities. Keep general role prompts independent of the current execution environment.

### Campaign artifacts

Use for objective-specific observations, measurements, hypotheses, roadmap state, and discovered quirks. Pass paths to these artifacts; do not promote their contents into durable prompts by default.

## Protect Role Boundaries

The effectiveness auditor may diagnose planning quality and propose a VibeSys change, but must not take over candidate design. Candidate judges audit individual implementations; the effectiveness auditor audits the behavior of the entire loop over time.

One agent may assess and propose a meta-intervention for simplicity. Framework-owned evidence, predeclared metrics, and a later audit must decide whether that intervention worked.

## Generality Gate

Before proposing reusable policy, ask:

- Would the mechanism occur in another domain or environment?
- Does the intervention encode the observed answer, or improve how answers are discovered?
- Is the right home a framework feature, neutral prompt, domain skill, runtime adapter, or campaign-local note?
- What legitimate exploration might the new rule suppress?

Keep one-off workarounds local. Promote recurring methods into skills and recurring deterministic mechanics into framework code.
